# Pack: artifact contracts between units

Switch on in the profile when units are separate repos (or separately released parts) that
consume each other's output: a library and its app, a data repo and its readers, an engine and
the product that runs it.

## Rule: units meet at a published, versioned artifact

A consumer never reads a producer's working tree or integration branch at run time. It reads
an artifact that is published, versioned and pinned:

| Artifact | Pinned by the consumer in | Checked by |
|---|---|---|
| API or RPC contract | a contract version (`contract_major`), JSON Schema files in the producer | schema validation in both repos' tests |
| Built package or binary | a lock file: name, version, sha256, url | checksum on download; the producer's status index |
| Data release | a tag plus a manifest sha256 | manifest check in the consumer's tests |
| Facts and pins (versions, commits) | one source-of-truth file in one repo | a CI check in every repo that names them |

The profile's "Contracts" section lists each one: producer, consumer, artifact, where the pin
lives, what checks it.

## Order of work

1. The contract or format change is its own issue in the producer, merged and released first.
2. The consumer bumps its pin in its own PR, with the checksum verified by the reviewer, not
   copied from the agent's report.
3. Only then does feature work that needs the new version start.

When both sides must change together, the producer ships the new version next to the old one;
the consumer switches; the old one is removed later.

## Status lives outside the artifact

An artifact is immutable once published (its checksum is pinned). Whether it is `stable`,
`experimental` or `revoked` is recorded in an index next to it, on the producer's release
branch. Promotion never changes a pinned checksum.

## Reference tests

When a unit must reproduce another system's output (a vendor tool, a previous
implementation), it keeps reference ("golden") tests against the real thing:

- First compare the reference with itself. What differs between two runs of the reference is
  noise or randomness, not a bug in your side.
- Every normalisation rule needs evidence written down next to it. A rule that edits only one
  side's input is a review point.
- Features the reference randomises get their own verdict (for example `engine_random`), never
  a looser comparison of a strict case.
- A package is `stable` only after its reference tests pass; until then it is `experimental`
  and consumers do not use it by default.

## Checklist (adds to the core checklist)

- The contract changed only through its own issue; version bumped; changelog updated.
- A released major version is not broken.
- Pins come from the source-of-truth file, never typed from memory.
- Lock bumps: the reviewer recomputed or looked up the checksum.
- Generated files are regenerated by their script, never edited by hand.
- Claims about another system carry a citation (`repo@commit:path#Lx-Ly`) or `UNVERIFIED`.
- Licence boundaries hold: code under a copyleft licence is not imported, vendored or linked
  into a closed unit; only the process or network boundary is crossed.

## Usual profile choices

`multi-repo`; one unit per repo; coordinator releases producers, the owner releases what users
see; `continuous` cadence with a release per unit; the Reviewer mandatory on contract and lock
changes.
